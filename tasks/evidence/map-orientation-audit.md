## Detailed map: square, unrotated axes

`reference-private/observations/listings-20260927/carte.json`:

- 0x0128: `cdefmap ... 16 0 16` configures 16-pixel tile axes.
- 0x013d: `csetmap ... 320 ... 150` configures a 320×150 map viewport.
- 0x086a: `cputmap ... (main+0x2fae * 16) ... (L0x3aw * 16)` supplies the
  x/y window offsets in tile pixels.
- Initial window x = train x−10 (0x00a5), clamped0..140 (0x00b1–0x00d6).
  Initial window y = train y−4 (0x00f7), clamped0..63 (0x0102–0x0123).
  It is a local window near the train, not a bounding box of explored tiles.

Independent renderer source:
`reference-private/alis-source/src/image.c`, `draw_transarctica_map`, lines4074–4311.
It reads the column-major map using `tileoffset`, then places each bitmap with
`posx1 = (mapwidth - mw) * tilex` and
`posy1 = ((mapheight - mh) - addy) * tiley + (((tiley - 1) - height) / 2)`.
The last term centres taller tile art; it is not an isometric projection.
`tileaddr += tileoffset` advances one map column; the end-of-row adjustment
advances the map row. Thus increasing x moves right, increasing y moves down.

Original logical axes are **east=(16,0), south=(0,16)** pixels per cell.
A modern uniformly enlarged presentation can retain these directions and equal
axis scale without retaining literal 16-pixel art. No oblique rotation is attested.

CARTE.FIC storage is160×73 bytes, addressed `data[x*73+y]` (`FORMAT-CARTE.md`,
`world_data.gd`). This gives a decoded full tile-image extent2560×1168 pixels.
Some original traversal/mask bounds use y0..71 and the viewport clamps to63;
do not delete or reinterpret the storage's73rd row from this audit alone.

Existing corroborating decode:
`reference-private/art-direction/decoded-20260927/decoded-detailed-map-full.png`
and `raw/carte_tiles_1_151_pal0.png`, generated by `tools/claude/visuals/mapr.py`.
That helper lays column x at x*16 and row y at y*16. Its illustrative start
capture uses y=train_y−5, which is **not** the exact original window start
above (−4); the helper is not a camera oracle.

## Discrepancies observed before correction and affected code

1. `game/scripts/travel_world.gd` defines WORLD_EAST=(180,100) and
   WORLD_SOUTH=(−180,100). `_project` therefore draws an eastward step down-right
   and a southward step down-left. This is a rotated/sheared diamond map, unlike
   ECS03 and the tile renderer. `_unproject` is specifically its oblique inverse.
2. `game/shaders/travel_ground.gdshader` independently hardcodes the same180/100
   forward/inverse formulas. Replacing GDScript constants alone would leave
   ground sampling and discovery coordinates misaligned with the rails.
3. `game/scripts/world_view.gd` already uses x-right/y-down coordinates, so its
   error is **not** another rotation. It draws a procedural rail chart, discovers
   tiles, hides undiscovered cells, and `fit_discovered()` fits only the visited
   bounds. The coordinator opens this as the overview. It cannot reproduce the
   whole original fixed plan shown in ECS04.
4. `tasks/evidence/map-discovery.md` already establishes that the original
   detailed renderer does not consult a persistent explored-cell fog mask.
   Mobile-unit observation rules are separate. Do not present the remake's
   persistent fog as an original map rule.
5. Train rendering uses `_project` and WORLD_EAST.length() to preserve a fixed
   displayed chord (`train_renderer.gd`), and tests presently describe the
   projection as oblique. An axis correction must preserve the owner's equal
   on-screen vehicle-length requirement, input hit-testing and rail attachment.
   This audit does not authorize switching train art style or shortening wagons.

## Supported correction and acceptance evidence

- Detailed map: use perpendicular equal-scale screen axes, east right and south
  down. Update both forward and inverse transforms and the ground shader together.
  Keep train/rail/switch picking under the same transform. Preserve fixed vehicle
  display lengths across headings.
- General map: show the full original plan's layout and landmark content at the
  correct aspect ratio, using a private reference to author replacement artwork.
  Keep historical pixels/datasets private. Position world markers using the
  decoded general-map transform; do not infer it from the oblique scene.
- Separate general/detailed views as the original does. A faithful general map
  must not start as a small fogged patch because of `fit_discovered()`.
- Native acceptance: at one known position, an x-only move stays at the same
  screen y, a y-only move stays at the same screen x; projection/picking roundtrip
  remains correct. Compare captures side by side with ECS03/ECS04. Verify the
  whole plan, compass/scale placement, marker location and lower instrument strip.
  Run existing vehicle-size and switch-input tests after changing transforms.

No runtime claim or implementation benchmark is made here. The screenshot
comparison, exact decoded geometry and renderer source agree on orientation;
original general-map text/landmark reproduction still needs an authored-art review.

## Implemented correction and measured checks

The owner subsequently authorized square-axis projection. `travel_world.gd`
now uses east=(CELL_PIXELS,0), south=(0,CELL_PIXELS), where
CELL_PIXELS=sqrt(180²+100²), the previous east-axis length. This authored scale
preserves vehicle chords in pixels. The inverse divides by CELL_PIXELS; the
ground shader receives the same scale as a uniform. No automatic zoom, route
simulation or `world_view.gd` behavior was changed by this correction.

Measured with native Godot 4.5:

- Before: headless `test_travel_world.gd` exited 1, failing the two new assertions
  that east-only movement stays horizontal and south-only movement stays vertical.
- After: the same suite exited 0, including axes, inverse/picking, bent-convoy
  fixed chords, switch clicks and interpolation.
- `test_camera_scale.gd` exited 0 both headless and in a native rendered macOS
  window (OpenGL Compatibility on Apple M4). It verifies preserved vehicle pixel
  scale, shader scale, fixed zoom, oversized-train framing and manual zoom.
- `test_train_renderer.gd` exited 0 with the actual updated projection.
- Diff whitespace checks passed. Owned test processes exited normally.

Logs remain in registered scratch `.cache/logs/`: `map-orientation-before.log`,
`test_travel_world-orientation.log`, `test_camera_scale-orientation.log`,
`test_camera_scale-orientation-native.log`, and `test_train_renderer-orientation.log`.
Root will preserve final review evidence before cleanup. The general-map redesign
is separate; these checks do not establish acceptance of the complete map visuals.

## Exact private general-plan extraction

`python3 tools/export_general_plan.py` exports resource192/palette196 to ignored
`reference-private/general-plan.json`. It does not consult CARTE.FIC. Schema:

    version: 1
    width: 320
    height: 149
    palette: sixteen [red, green, blue] entries
    rows: 149 arrays of [palette_index, run_length] pairs, left to right
    source: script path, source SHA256, image/palette resource IDs, index SHA256

Each row expands to exactly320 indices. There are8178 runs; the JSON is58909
bytes. Independent decoding of the packed source nibbles reproduced all47680
indices, byte for byte. Source SHA256:
`7709d64c391eaf98a1975b1de9425636c6db980c06a435a5c0081e3df9cf8b37`.
Expanded index SHA256:
`f85b3f98c7323565b3af263e841c3102d1f00fab4b3162906cd2c5ce6247af5a`.
Git ignore was verified in the main checkout (the worktree private directory
is a symlink). This full historical layout stays private even when represented
as JSON rather than a PNG; recolouring it does not make its geometry authored.

The exact sixteen RGB values live in that private JSON. Source pixels use
indices1 and6–14. Visual associations:9–12 cover olive/paper shades,13 the
light field,14 blue town/cartouche markings; dark indices also draw frame,
compass and lettering. These are colour descriptions, **not** a decoded
semantic feature map. A palette index cannot safely be labelled “rail” and
converted wholesale into gameplay geometry. A renderer may substitute an
authored palette while leaving every indexed run in its original position.

### Dynamic markers and inspection lens

The background contains the static plan. Runtime additions are separate:

- Train anchor: resource198, x=2*world_x+2, z=196−2*world_y
  (CARTE0x1ece, repeated when coordinates change at0x202f).
- Direction blink: CARTE0x25ac checks brake off and speed positive, chooses
  resource199+heading_selector and changes its vertical side near the top edge
  (0x25d3/0x25fd). Otherwise it draws resource247, the stopped cross (0x2627).
  Do not treat the fixed resource198 as the whole moving/stopped presentation.
- Mine dots: resource207, x=2*(stored_mine_x+40), z=195−2*stored_mine_y,
  at0x2571; active/exhausted status affects its blink layer.
- Lens: resource194 is the image, composite195 places it with relative offsets
  (9,0,−9). CARTE0x1f21–0x1f87 hides the pointer over the map, clamps mouse
  x to19..300 and mouse z to59..187, then draws195 at that mouse anchor.
- Lens coordinate labels: CARTE0x235b–0x244a displays x=mouse_x/2 and
  y=(193−mouse_z)/2, with x beneath and y to the right. On click,0x1fce or
  0x1fed sends those coordinates with message3 or14 according to the caller.
  This click transform is intentionally recorded separately from the train
  marker anchor; it is not simply the algebraic inverse of that marker offset.

These formulas were read from the existing private CARTE listing. The lens
is an inspection control, not proof that the static plan contains every live
rail or current unit. Original datasets and sprites remain excluded from
public assets and distributable bundles.

### Lens dimensions and ordinary click target

Resource194 is a transparent80×46 bitmap. Applying composite195's(9,0,−9)
offset with centred sprite placement puts its full bitmap at screen
(mouse_x−30,mouse_y−13), width80,height46. Source pixel inspection places
the main rectangular frame at local x6..52,y0..25; the inner clear aperture
is approximately x13..48,y6..19 (bevelled corners). The handle extends down
and right to roughly local x70,y45. These bounds distinguish the glass frame
from the much larger whole sprite including its handle.

For ordinary overall-map mode(CARTE local0x0c=1), clicking sends YODA message3
at0x1fce. YODA0x0020 routes messages3/14/15 to0x00c1, which saves the supplied
coordinates and starts0x2eef. That routine creates CARTE, supplies target x/y,
sets local0x0d=1 to use those coordinates, and for message3 sets main+0x2faa=1:
the ordinary detailed map. Message14 also creates a detailed map but sets
local0x0c=14 and main+0x2faa=15, a special caller mode. It does not mean
“switch to the general map”. The normal overview click should follow message3.
